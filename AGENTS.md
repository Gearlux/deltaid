# Deltaid Mandates

- **Standard Lightning Segmenter + smp Models (2026-07 — supersedes "Adapter, Not Segmentor"):** `deltaid.segmenter.LightningSegmenter` is ONE self-contained standard `pytorch_lightning.LightningModule` — its OWN step functions + a `run()` that builds loaders + `pl.Trainer` and dispatches on a `task` knob (`fit`/`evaluate`/`test`/`predict`, `@entrypoint`-annotated). It replaces the old trainer+evaluator pair (both subclassed the deleted `marainer` bases). Segmentation defaults it owns: `ignore_index` CrossEntropy loss + the mean-IoU / Dice metric pair (built eagerly when `num_classes` is given, else read off the model head in `initialize()`). Marainer is used ONLY for optional tracking + `marainer.torch` utils (removing it needs a few line changes). `DeepLabV3PlusModel` stays a thin `@configurable` smp wrapper. Run via `deltaid train/evaluate/predict cfg.yaml` or `sampleflux run cfg.yaml`.
- **Per-Pixel Target Contract:** Targets are int64 per-pixel class-id masks; logits are `[B, C, H, W]`. `LightningSegmenter` constructs the loss internally as a plain `torch.nn.CrossEntropyLoss` with `ignore_index` exposed as a segmenter param — there is no deltaid-owned loss adapter class. Any user-supplied override MUST be a class from `torch.nn`, `torchmetrics`, `segmentation_models_pytorch.losses`, `kornia.losses`, or another upstream library, passed verbatim under the segmenter's `loss_fn` / `*_metrics` YAML keys. Don't introduce one-hot intermediates.
- **Generic Primitives Live in Waivefront:** Rasterization ops (`waivefront.targets.RegionsToSegmentationMaskOp`, target-only — it writes the `[H,W]` mask and leaves the input PIL; chain the generic `sampleflux.ops.torch.ToTensor` to materialize the image tensor) and segmentation predictions sinks belong in `waivefront`, not `deltaid`. Deltaid stays focused on the model + collate + the `LightningSegmenter` specialisation.
- **Collate Discipline — Wire the Generic `sampleflux.typed_collate`:** `LightningSegmenter` wires `sampleflux.typed_collate` as its DataLoader collate — there is NO bespoke deltaid collate (the old `segmentation_collate_fn` was deleted). The config pipeline tensorizes the `[3, H, W]` `Image` input, and the segmentation `Mask` target is a fully-stackable array item, so `typed_collate` stacks BOTH the input (`[N, 3, H, W]`) and the mask target (`[N, H, W]`) and gathers aux fields as per-sample lists. The model boundary in `deltaid.segmenter` unwraps them (`_batch_input`, `_batch_target` — promoting the mask to `int64` for the pixel-class CrossEntropy contract) and transposes aux fields into a per-sample metadata list (`_batch_metadata`) for prediction sinks. Don't reintroduce a deltaid collate.
- **Encoder Selection from YAML:** `DeepLabV3PlusModel.__init__` MUST forward `encoder_name`, `encoder_weights`, `num_classes`, and other smp constructor knobs verbatim. Don't shadow names; don't silently rewrite defaults.
- **Single-Pass Baseline First:** DeepLabV3+ is the first-class single-pass baseline. Multi-stage / cascade architectures (HRNet, UperNet, etc.) are additions, not replacements — keep the smp-backed surface minimal.
- **Discovery Tags (`task`/`role`):** Deltaid tags its classes `@configurable(task="segmentation", role=…)` — `DeepLabV3PlusModel` is `role="model"`, and the merged `LightningSegmenter` is `role="trainer"` (its evaluate/test/predict capabilities are the SAME class, declared via its `@entrypoint`-annotated methods — there is no separate evaluator class or `role="evaluator"` tag). Each derives the matching `category`, e.g. `segmentation_model`, so navigaitor's `list_configurable_classes(category=…)` / `list_classes(task=…, role=…)` and the visual-editor form-spec offer them. Preserve the tags when adding/renaming — `tests/test_categories.py` pins them; a dropped tag silently empties the corresponding picker and drops the segmenter out of navigaitor's `role="trainer"` scan (`TASK_REGISTRY` + `generate_task_config`). (The loss is a plain `torch.nn.CrossEntropyLoss` built in the segmenter, so there is intentionally no `segmentation_loss`-tagged class.)
- **Explicit or model-head `num_classes`:** `LightningSegmenter` takes `num_classes: Optional[int] = None` and builds its metrics **eagerly** when a count is given; when omitted, `initialize()` reads `num_classes` off the concrete model head (raising if it cannot be determined) and builds the metrics then — there is no dataset-dimension-derivation layer (the generic `marainer.dimensions` layer was removed). Prefer **providing `num_classes` explicitly** (on the segmenter / model config); the model-head read is the fallback. The resolution logic lives in `LightningSegmenter.initialize()` (there is no separate `marainer` base flow) and mirrors `sonair.LightningClassifier`.
