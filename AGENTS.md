# Deltaid Mandates

- **Standard Lightning Segmenter + smp Models (2026-07 — supersedes "Adapter, Not Segmentor"):** `deltaid.segmenter.LightningSegmenter` is ONE self-contained standard `pytorch_lightning.LightningModule` — its OWN step functions + a `run()` that builds loaders + `pl.Trainer` and dispatches on a `task` knob (`fit`/`evaluate`/`test`/`predict`, `@entrypoint`-annotated) — **`run()` dispatches through `recordstream.runnable.run_entrypoint(self, self.task)`, so those markers ARE the dispatch table; do NOT reintroduce a hand-written `{task: method}` dict** (2026-07-29; rationale: recordstream `docs/architecture.md` §7). It replaces the old trainer+evaluator pair (both subclassed the deleted `marainer` bases). Segmentation defaults it owns: `ignore_index` CrossEntropy loss + the mean-IoU / Dice metric pair (built eagerly when `num_classes` is given, else read off the model head in `initialize()`). Marainer is used ONLY for optional tracking + `marainer.torch` utils (removing it needs a few line changes). `DeepLabV3PlusModel` stays a thin `@configurable` smp wrapper. Run via `deltaid train/evaluate/predict cfg.yaml` or `recordstream run cfg.yaml`.
- **Per-Pixel Target Contract:** Targets are int64 per-pixel class-id masks; logits are `[B, C, H, W]`. `LightningSegmenter` constructs the loss internally as a plain `torch.nn.CrossEntropyLoss` with `ignore_index` exposed as a segmenter param — there is no deltaid-owned loss adapter class. Any user-supplied override MUST be a class from `torch.nn`, `torchmetrics`, `segmentation_models_pytorch.losses`, `kornia.losses`, or another upstream library, passed verbatim under the segmenter's `loss_fn` / `*_metrics` YAML keys. Don't introduce one-hot intermediates.
- **Generic Primitives Live in Waivefront:** Rasterization ops (`waivefront.targets.RegionsToSegmentationMaskOp`, target-only — it writes the `[H,W]` mask and leaves the input PIL; chain the generic `recordstream.ops.torch.ToTensor` to materialize the image tensor) and segmentation predictions sinks belong in `waivefront`, not `deltaid`. Deltaid stays focused on the model + collate + the `LightningSegmenter` specialisation.
- **Collate Discipline — Wire the Generic `recordstream.collate_records` (record model, 2026-07-26):** `LightningSegmenter` wires `recordstream.collate_records` as its DataLoader collate — there is NO bespoke deltaid collate. A record is a plain dict addressed by CONFIGURED keys: `LightningSegmenter(input_key="image", target_key="target")` (the recordstream target ops' default `output`). The config pipeline tensorizes the input, and the segmentation `Mask` target is a fully-stackable array item, so `collate_records` stacks BOTH the input (`[N, 3, H, W]`) and the mask target (`[N, H, W]`) and gathers the remaining keys as per-record lists. The model boundary reads them back through recordstream's GENERIC readers — `batch_tensor(batch, key, device)` for the input and `batch_metadata(batch, exclude=(input_key, target_key))` for the per-record metadata prediction sinks need. **deltaid's private `_batch_input` / `_batch_metadata` were DELETED 2026-07-29** and moved to `recordstream.batch` (the inverse of `collate_records`, living beside it) — they were a near-verbatim duplicate of another consumer's copy, with a duplicate test file to match; do not reintroduce them. `_batch_target` is GONE too (2026-07-29): `batch_tensor` grew a `dtype=` parameter — the same knob as `device`, where recordstream honours the contract the caller names rather than deciding one — so the segmenter simply calls `batch_tensor(batch, self.target_key, dtype=torch.int64)` for the pixel-class CrossEntropy contract. Do not reintroduce a wrapper whose whole body is a dtype cast. Don't reintroduce a deltaid collate.
- **Deferred Slots Are Declared `Lazy[T]`, Never `Any` Or A Hand-Written Union (2026-07-29):** a slot this class flows ITSELF at run time — `model` (flowed with `num_classes=`), `train_set`/`test_set`, and the body slots `optimizer` (`params=`), `train_loader`/`val_loader`/`test_loader` (`dataset=`), `lightning` — MUST be annotated `Lazy[T]` (composed as `Mandatory[Lazy[T]]` where required). Two spellings are PROHIBITED: (a) `Optional[Union[X, Fluid]]`, which hand-writes confluid's alias — `Lazy = Annotated[Union[T, Fluid], _LAZY_MARKER]` — and silently drops the marker; (b) a bare `Any`, which type-checks nothing. What the marker buys differs by slot kind and the difference is REAL: for CONSTRUCTOR params it is machine-read (`confluid.lazy_param_names` reports them; liquifai's auto deep-flow SKIPS them instead of eagerly building a target that needs a runtime kwarg), while for BODY slots `lazy_param_names` scans `__init__` params only, so the marker is inert there and deferral is enforced by the slot holding a `LazyClass` value — the annotation still earns its place by giving `to_pydantic` a real type for navigaitor's form-spec / StreamStudio widgets. Before this landed, `lazy_param_names(<this class>)` returned an EMPTY set while the code flowed those very slots by hand. Dataset slots use the shared `marainer.torch.RecordSource` alias (`Dataset | Iterable[Record]` — the contract `ensure_record_dataset` enforces), never a locally-invented union. Follow-up filed in confluid TASKS: teach `lazy_param_names` to scan body slots the way `to_pydantic` already does.
- **Encoder Selection from YAML:** `DeepLabV3PlusModel.__init__` MUST forward `encoder_name`, `encoder_weights`, `num_classes`, and other smp constructor knobs verbatim. Don't shadow names; don't silently rewrite defaults.
- **Single-Pass Baseline First:** DeepLabV3+ is the first-class single-pass baseline. Multi-stage / cascade architectures (HRNet, UperNet, etc.) are additions, not replacements — keep the smp-backed surface minimal.
- **Discovery Tags (`task`/`role`):** Deltaid tags its classes `@configurable(task="segmentation", role=…)` — `DeepLabV3PlusModel` is `role="model"`, and the merged `LightningSegmenter` is `role="trainer"` (its evaluate/test/predict capabilities are the SAME class, declared via its `@entrypoint`-annotated methods — there is no separate evaluator class or `role="evaluator"` tag). Each derives the matching `category`, e.g. `segmentation_model`, so navigaitor's `list_configurable_classes(category=…)` / `list_classes(task=…, role=…)` and the visual-editor form-spec offer them. Preserve the tags when adding/renaming — `tests/test_categories.py` pins them; a dropped tag silently empties the corresponding picker and drops the segmenter out of navigaitor's `role="trainer"` scan (`TASK_REGISTRY` + `generate_task_config`). (The loss is a plain `torch.nn.CrossEntropyLoss` built in the segmenter, so there is intentionally no `segmentation_loss`-tagged class.)
- **Explicit or model-head `num_classes`:** `LightningSegmenter` takes `num_classes: Optional[int] = None` and builds its metrics **eagerly** when a count is given; when omitted, `initialize()` reads `num_classes` off the concrete model head (raising if it cannot be determined) and builds the metrics then — there is no dataset-dimension-derivation layer (the generic `marainer.dimensions` layer was removed). Prefer **providing `num_classes` explicitly** (on the segmenter / model config); the model-head read is the fallback. The resolution logic lives in `LightningSegmenter.initialize()` (there is no separate `marainer` base flow) and mirrors `sonair.LightningClassifier`.
