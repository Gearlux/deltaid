- **A Model Wrapper NAMES The Weights It Loads — `model_refs` (2026-08-02):** every `@configurable` model wrapper here exposes a `model_refs` property returning a LIST of `matrainer.uri.ModelRef` (`uri` / `url` / `role`), which the tracking layer walks off the configured graph into the run manifest's `models` section — NO consumer calls anything. A LIST because a wrapper composes artifacts: an smp encoder plus a checkpoint over it is two, and each carries the `role` it played (`pretrained` = from outside the run, `checkpoint` = from a previous run of ours). **THREE rules, all load-bearing:** (1) **read STORED CONFIG ONLY** — the property is asked of a wrapper that may never run, so it must never build, download or open anything (pinned by `tests/test_model_refs.py`, which asserts the lazy cache is still `None` afterwards); (2) **report an EMPTY list when nothing external was loaded** — random weights referenced no artifact and the architecture is already in `params`; inventing a reference would name something nobody loaded; (3) **use the shared `hf_model_ref` / `file_model_ref` helpers** rather than formatting a URI by hand, so the same weights reached through two wrappers produce the SAME string. A zoo with no repository page names its registry + entry (`smp://<arch>/<encoder>?weights=<set>` — smp routes each encoder's weights through a different upstream registry, so a single repository URL would be wrong for most of its ~800 encoders) and reports NO `url` rather than inventing one. Adding a model wrapper means adding this property; a wrapper with no external weights (the shared-spec convnets) needs NOTHING, because the protocol answers empty for a class that does not implement it.

Its `!scope:framework=torch` block in the example config is the smallest in the file, which is the point. **What it does NOT have, and why that is honest rather than missing:** no `lightning:` Trainer slot and no framework loggers (tracking goes through `trackers:`, which every backend has, via matrainer's plain FUNCTIONS `log_run_context` / `capture_log_file`, hookup style (1)); no callback protocol; no distributed strategy. Multi-GPU is out of scope ON PURPOSE — that is what Lightning is for, and a half-Trainer here would be a worse one. Ctor knobs the others lack: `device` (matrainer's closed `Literal["auto","cpu","cuda","mps"]` — the CHOICE is `matrainer.torch.resolve_device`, not a private function here, because a `Trainer` picks an accelerator for you and every hand-written loop picks identically), `checkpoint_dir` (a plain `state_dict` — there is no framework format), `grad_clip`. - **The fastai Backend Swaps The LOOP And Nothing Else — And Its Loss Axis Is A TRAP (2026-08-02):** `FastaiSegmenter` runs on torch, so it reuses `SegmentationModelPytorch` unchanged, the `[N, 3, H, W]` batch shape, `collate_records` and the torch losses — the `fastai` block in the example config overrides `runnable` and `metrics` and nothing else. What it owns is three things, and TWO are measured facts about fastai: (1) **`_to_tuple`** — fastai unpacks a batch POSITIONALLY, so the batch must BE a tuple rather than the record dict a `LightningModule` reads by key; the loaders are the Lightning backend's construction with exactly ONE kwarg changed (`collate_fn=self._to_tuple`), and `predict()` reuses the SAME `test_loader` slot with a runtime `collate_fn=collate_records` override so the sink gets its record dicts while every operator-set knob still applies. (2) **THE LOSS NEEDS `axis=1`, and fastai's default is WRONG for segmentation:** `CrossEntropyLossFlat` defaults to `axis=-1`, which flattens the CHANNEL dimension of an `[N, C, H, W]` prediction into the batch and dies with *"Expected input batch_size (48) to match target batch_size (128)"* (measured); with `axis=1` it agrees with `torch.nn.CrossEntropyLoss` to seven decimals (measured). Nothing in the config hints at it, which is why the DEFAULT states it rather than leaving it to the user. (3) **The METRICS need no such fix, and that asymmetry is the tell:** `DiceMulti` and `JaccardCoeffMulti` already default to `axis=1` because they exist FOR segmentation — only the loss, which is shared with classification, carries the wrong default. **Metrics are NAMES, not `!class:` tags:** `foreground_acc` is a plain function while `DiceMulti` is a class fastai instantiates itself (`mk_metric` does `if isinstance(m, type): m = m()`), so there is nothing uniform for a tag to resolve or for confluid's registry to tag — do NOT add a metric-wrapper class to make them registrable. **`metrics:` MUST be restated in the fastai config block**, and that is not style: the shared `metrics:` key is a torchmetrics TEMPLATE MAPPING, which a `Learner` cannot consume. **`train_metrics` IS served since 2026-08-05** — see the per-split mandate; the claim that stood here ("a `Learner` computes its metrics on the validation pass only") described fastai's DEFAULT rather than a constraint. `from fastai.callback import schedule  # noqa: F401` is load-bearing: `fit_one_cycle` is a `@patch` installed as that module's IMPORT SIDE EFFECT and fastai's `@patch` returns `None`, so importing the function by name binds None and `learn.fit_one_cycle` then falls through fastcore's attribute delegation to the MODEL. fastai's `Learner` ALWAYS validates, so `_dataloaders()` reuses the TRAINING data when no `val_set` is wired and warns that the metrics then measure fit, not generalization. **ONE metric name is CONFIGURED rather than resolved, and it is the exception that proves the names rule — `pixel_accuracy` (`PixelAccuracy`, 2026-08-05):** `fastai.metrics.accuracy` argmaxes over `axis=-1`, which on an `[N, C, H, W]` prediction is the WIDTH, and `foreground_acc` scores ONE class rather than all pixels — so the quantity the other seven engines report was unreachable by NAME and left the sweep's `val/pixel_accuracy` column blank on this row alone. It wraps NOTHING (there is no upstream metric to wrap), so it is not the metric-wrapper class the rule above bans; what it supplies is the ACCUMULATOR, exactly as fastai's own `DiceMulti` does for its quantity. `AvgMetric(partial(accuracy, axis=1))` would have been one line and is WRONG the moment `ignore_index` drops a varying number of pixels per image, because fastai weights a per-batch average by BATCH SIZE rather than by counted pixels (pinned by a two-batch case where the batch-weighted answer is 0.5 and the true one 0.8). `_as_metric` takes the segmenter's `ignore_index` and tries `_METRIC_ALIASES` FIRST, since an alias exists precisely where the upstream name would resolve to the wrong thing; its `name` property is `pixel_accuracy` because a metric reported under its class name would open a column no other row fills. The precedent is the classification project's `f1_macro` alias, and the trigger is identical. **Verified end to end 2026-08-02:** `deltaid train --framework fastai` on the 256-row slice — dice_multi 0.6238 → **0.8254**, jaccard 0.5054 → 0.7263 over five epochs.
- **A FORKED DataLoader Worker Needs TWO Guards, And This Project Is Where The Second Was Found (2026-08-02):** `import fastai` sets the multiprocessing start method to **`fork`** at import — PROCESS-WIDE, so every backend sharing that interpreter inherits the hazard, not just fastai. A forked child inherits memory but NOT threads, and it dies with a **SIGSEGV and no Python traceback**, surfacing only as `DataLoader worker exited unexpectedly`. Both guards are recordstream's and BOTH are needed: **(1) `ensure_materialized(source)`** — every backend routes each wired split through a `_prepare()` helper that calls it beside `ensure_record_dataset`, so a lazy source is built in the PARENT rather than through `_scproxy` in the child; **(2) `cv2.setNumThreads(0)`**, which recordstream now fires itself the first time it invokes an albumentations op. **Neither fixes the other** (measured: warmed source + live cv2 pool still SIGSEGVs; cold source + no pool is still built in the child). **Why segmentation found this and classification never did:** a classification config resizes with `ConvertToImage` (PIL), while a per-pixel task must resize the image and its mask in ONE JOINT DRAW — which only a bare albumentations transform does, so segmentation is the first thing in the workspace to put cv2 on the worker path. Do NOT "fix" a recurrence by setting `num_workers: 0` — that avoids the fork rather than the bug, and makes the crash look flaky. Pinned fleet-wide by `tests/test_tracking_parity.py::test_every_backend_warms_its_sources_before_forking`, and upstream by `recordstream/tests/test_fork_safety.py`.
- **The SHARED U-NET SPEC Is A PACKAGE, Apart From The Zoo Wrapper — `deltaid/unet/` vs `smp_model.py` (2026-08-02):** the two kinds of model here answer different questions and only look alike because both end in a per-pixel head. A **zoo wrapper** (`SegmentationModelPytorch`) exists to reach somebody else's weights, and its knobs are about the zoo — an architecture name, an encoder, `encoder_weights`, a checkpoint; it stays at the TOP LEVEL, one `<backend>_model.py` each. A **U-Net** implements `deltaid/unet/spec.py` and wraps NOTHING; its knobs are the architecture itself (`widths` / `bottleneck_width` / `seed`), and its whole reason to exist is that the implementations are the SAME network — a claim about the OTHER implementations rather than about its own backend. **It exists because the zoos do not line up:** smp is torch-ONLY, so a cross-framework comparison built on it could never include Keras, Flax or MLX, and four zoo models would compare four networks instead of four frameworks. `spec.py` owns the constants AND **derives** `trainable_parameter_count` (488,739 for 3 classes with the defaults), so each implementation is checked against the CLAIM rather than against whichever was written first — the layer ORDER is prose, because different APIs cannot share code, and the derived count is the only thing holding them together. **Three spec choices exist to keep the implementations comparable rather than because they are best:** upsampling is parameter-free NEAREST (a learned `ConvTranspose2d`'s parameter count and output size depend on padding conventions that differ between frameworks, which would make "the same network" untrue by construction); `H`/`W` must be divisible by `2 ** len(widths)` (`size_divisor()`, a function because it follows from `widths`); and the `input_shape` KNOB stays `(H, W, C)` in every implementation so one config line drives any of them, even though `TorchUNet`'s TENSOR is NCHW. **`TorchUNet` serves ALL THREE torch backends** — they differ in the loop, not in what a model is — which is why there is no `fastai_unet.py`, exactly as there is no `fastai_model.py`. **`deltaid/unet/__init__.py` imports NOTHING and that is load-bearing:** `deltaid/__init__.py` resolves every backend name lazily so a machine without torch never imports it, and an `__init__` re-exporting the implementations would drag in torch (and later keras / flax / mlx) the moment anything under the package — including the dependency-free `spec.py` — is touched. Do NOT add re-exports there, do NOT re-merge an implementation into the zoo module, and do NOT add one that is not an instance of its framework's own module type.
- **The Keras Backend Changes The LAYOUT And The LOSS VOCABULARY, Nothing Else — `KerasSegmenter` (2026-08-03):** the fourth backend and the first that is not torch. Everything upstream of the model is recordstream's unchanged, INCLUDING the batching: `recordstream.keras.RecordSequence` is the `keras.utils.PyDataset` a `DataLoader` would have been, and `_to_arrays` is handed to it exactly as a `collate_fn` is handed to a `DataLoader`. TWO real differences, both about the ENGINE and both living in the CONFIG where a reader can see them: **(1) Keras is channels-LAST**, so a Keras run's `preprocess` chain is the shared one MINUS its final `ToTensor` (which produces CHW) — the MASK needs no change, being `[N, H, W]` in every engine, so ONLY the image line differs; **(2) `from_logits=True` is MANDATORY** on the loss, because the head is a bare 1x1 conv and Keras's default expects PROBABILITIES: handed logits it normalizes by the ROW SUM and CLIPS rather than raising, so the loss stays finite and is merely WRONG (measured on one batch: 1.4546 correct vs 4.6293 wrong). The default metric additionally needs **`sparse_y_pred=False`** — `MeanIoU` otherwise expects an already-argmaxed prediction and raises a shape error on raw logits (measured). **`metrics` / `train_metrics` / `val_metrics` / `test_metrics` are UNIONED here, not merged** (`matrainer.metric_slots.union_metric_specs`): `keras.Model.compile` takes ONE list and reports it on train AND validation, and there is no hook that narrows a metric to one split short of recompiling between phases — which would discard the optimizer state a fit is using. Widening is the honest failure; DROPPING a wired metric would be a metric that silently reports nothing. Keras 3 picks its engine from `KERAS_BACKEND` and this module never sets it. **P5 (2026-08-07): built on the WORKSPACE KERAS-FAMILY BASES** — the concrete is now `(SegmentationKeras, matrainer.keras.KerasRunnable)` with the machinery (compile/fit, the History read-back, the RecordSequence boundary, the tracking callback, the harmonized evaluate-scores-VAL rule) in matrainer and the task's keras vocabulary in `segmentation_keras.py` — shared verbatim with the native-TensorFlow sibling. The fleet exemptions key on `KerasRunnable`/`TensorFlowRunnable` in the source and forbid shadowing the family wiring (`_callbacks`/`_compile`/`fit`/`initialize`); the machinery is pinned in matrainer's `tests/test_keras_family.py`.
- **`keras.metrics.MeanIoU` On The TORCH Engine Makes A Run Look HUNG — Warn, Never Substitute (2026-08-03):** `MeanIoU` / `IoU` / `OneHotMeanIoU` accumulate a `[C, C]` confusion matrix through `keras.ops.scatter`, and the torch backend implements that as a **Python loop over every index** (`keras/src/backend/torch/core.py`: `for i in range(indices.shape[0]): zeros[tuple(index)] += values[i]`). Per-PIXEL that index count IS the pixel count, so one 8x224x224 batch is 401,408 iterations. Measured on that batch: **tensorflow 0.009 s, jax 0.194 s, torch ~160 s**, against a 0.37 s model step — i.e. on torch the metric is ~99.8% of the run, and `deltaid train --framework keras` on this workspace's default engine appears to hang rather than to be slow. `_warn_if_the_engine_cannot_afford_these_metrics` fires ONCE at compile with the measurement and the fix (`KERAS_BACKEND=tensorflow`). **Do NOT "fix" it by defaulting to a cheaper metric on torch:** a default that changes with the engine breaks the ONE claim this project makes, that the same config gives the same run. Classification never hit this and the asymmetry is the tell — its metrics are per-IMAGE, so the same scatter loops over 8 indices instead of 401,408.
- **The TensorFlow Backend Is A SIBLING Of The Keras One, Not A Subclass — And Owns Only What Keras 3 Does Not Expose (2026-08-03):** `KERAS_BACKEND=tensorflow deltaid train --framework keras` already runs the identical config, so `TensorFlowSegmenter` earns its module by owning FOUR things Keras does not reach: a `tf.data.Dataset` with `prefetch(AUTOTUNE)`; `tf.GradientTape` steps under `@tf.function` (which is what makes `jit_compile`/XLA a knob at all); the epoch loop `fit()` would have run; and `_export`, the SavedModel — the one run artifact that is TensorFlow's and not Keras's. It is a SIBLING because it **narrows a precondition** its would-be parent does not have — `_require_tensorflow_backend()` raises where a `KerasSegmenter` runs fine — so a picker offering "any KerasSegmenter" would hand out something that cannot run. It still declares `framework="keras"`: the axis names the API a class is WIRED TO, and every one of its slots holds a `keras.losses` / `keras.metrics` / `keras.Model`. **There is deliberately no `tensorflow_segmentation.py`** — TF >= 2.16's `tf.keras` IS Keras 3, so a second loss module would register the same classes under a second tag and make every bare `!class:SparseCategoricalCrossentropy` ambiguous; `FRAMEWORKS["tensorflow"].registrations` names `deltaid.keras_segmentation`. Unlike the Keras backend this loop CAN honour a per-split metric set (each traced step closes over its own list), so it uses `merge_metric_specs`; because a Keras metric is a stateful ACCUMULATOR, `_as_metric` returns a FRESH object per split, cloning a live instance through Keras's own `get_config()`/`from_config()` (measured: the clone reports 0.0 where the original, after an update, reports 1.0). Two ordering rules are load-bearing: `deltaid/_tensorflow.py` `setdefault`s `KERAS_BACKEND=tensorflow` BEFORE importing anything that reads it and re-exports `keras` + `RecordSequence` so isort cannot sort a `recordstream.keras` line above it; and `fit()` calls `optimizer.build(...)` OUTSIDE the graph, because Keras builds slot variables on the first `apply_gradients` and creating variables during tracing is legal once and an ERROR on any retrace — which a short final batch is enough to trigger. **P5 (2026-08-07): built on `matrainer.tensorflow.TensorFlowRunnable`** — the loop machinery (tf.data, traced steps, per-split CLONED metric objects, the hand-driven CallbackList, the engine guard, the discovered-signature SavedModel export, the per-epoch `sequence.on_epoch_end()` reshuffle) is matrainer's, sharing the task's keras hooks with the compile/fit sibling.
- **`tf.initializers` IS Keras, So A Raw-`tf.nn` Module May Not Touch It (2026-08-03):** since TF 2.16 `tf.keras` is Keras 3, and `tf.initializers.GlorotUniform` resolves to `keras.initializers.GlorotUniform`. In a process where Keras is bound to the TORCH engine — which is exactly this workspace, since `recordstream.keras` defaults `KERAS_BACKEND` to the first engine installed and torch wins — it returns a **torch tensor**, and `tf.Variable` then dies converting an MPS tensor to numpy (*"can't convert mps:0 device type tensor to numpy"*). `TensorFlowUNet` therefore computes its own Glorot-uniform weights from `tf.random.stateless_uniform` (`_glorot_uniform`), which is also seed-reproducible where the stateful op reads a global seed another library can move. The bug is invisible until both engines share one interpreter, which is why the fleet test suite found it and a single-file run never would. **Any module claiming to be raw TensorFlow must be checked for `tf.keras`/`tf.initializers`/`tf.losses`/`tf.metrics` reach-throughs**, all of which are Keras.
- **The HuggingFace Backend Swaps The MODEL As Well As The LOOP — And Its THREE Quirks Are All The Model's (2026-08-03):** `HuggingFaceSegmenter` is the only backend whose block needs its own `model:`, and the only one with NO loss slot and NO registrations module (`FRAMEWORKS["huggingface"].registrations is None`) — an `AutoModelForSemanticSegmentation` computes its own loss from `labels=`, so there is nothing a config could wire. - **The JAX Backend Owns The WHOLE Loop, And Jits It ONCE — `JaxSegmenter` (2026-08-03):** the SEVENTH backend and the closest sibling of the TensorFlow one — both replace `fit()` with a traced step — where the differences between them are exactly the differences between the two programming models. The step is a PURE FUNCTION of `(model, batch)` that `nnx.value_and_grad` differentiates and `nnx.Optimizer` applies in place; randomness is EXPLICIT (the model carries its own `nnx.Rngs`, which is what makes `seed:` on `FlaxUNet` real). **`_make_steps()` is called ONCE and its result reused across epochs** — a fresh `nnx.jit` per epoch retraces the whole graph every time and ends up slower than the eager loop it replaced, the same trap `tf.function` has (pinned by `tests/test_jax_segmenter.py::test_the_steps_are_jitted_ONCE_and_reused`, which reads `fit`'s SOURCE). `jit: false` exists to read a Python traceback from inside a step. **Losses, metrics and optimizers are NAMES, not `!class:` tags:** optax ships plain FUNCTIONS and FACTORIES, so there is no class for a tag to resolve or for confluid's registry to tag — hence NO `jax_segmentation.py` and `FRAMEWORKS["jax"].registrations is None`. The default loss is `optax.losses.softmax_cross_entropy_with_integer_labels`, which takes `[..., C]` logits against `[...]` integer labels — so the `[N, H, W, C]` / `[N, H, W]` pair needs NO reshape and agrees with `torch.nn.CrossEntropyLoss` to seven decimals (measured, and pinned numerically rather than by name). **`ignore_index` is applied HERE, in `_loss_fn`, because optax's losses take no such argument:** the per-pixel loss is masked and the mean taken over the VALID pixels only, and the ignored label is CLAMPED to 0 first because it is not a valid class id and would index out of range. Dividing by the full pixel count instead would shrink the loss in proportion to how much of the image is void — a silent, image-dependent learning-rate change. Channels-LAST, so a JAX config's `preprocess` is the Keras/TensorFlow one. `RecordSequence` is reused verbatim — batching a record stream is not a JAX problem.
- **The MLX Backend Completes The SET — `MlxSegmenter`, and `FRAMEWORKS` is now finished (2026-08-03):** the EIGHTH and last backend, and every verb the CLI advertises is real. **What MLX contributes is three facts, and each shapes the loop rather than its spelling:** (1) **unified memory** — CPU and GPU share it on Apple silicon, so there is NO device transfer and this is the one backend whose batch path does genuinely LESS work than the others; (2) **arrays are LAZY** — `mx.eval` forces computation and omitting it does NOT raise, it grows the graph until memory runs out, so `fit()` evaluates once per step over `network.parameters()`, `optimizer.state` AND the loss, deliberately and visibly; (3) **train/eval is module STATE, not a per-call argument** — `network.train(True)` at the top of each epoch and `self.model.train(False)` in `_evaluate`, because a `training=False` DEFAULT on `__call__` would flip the network to eval on every forward, including the one inside `nn.value_and_grad` where there is no flag to pass, and batch-norm would then never train. Targets are **int32**, the one dtype in the fleet that differs from the int64 every other backend names: MLX indexes with int32 and its `cross_entropy` expects it. Note the asymmetry with JAX, which is the reason `_as_optimizer` is not shared: **optax ships FACTORIES (`optax.adam(lr)`) while `mlx.optimizers` ships CLASSES**, so this one INSTANTIATES where the JAX one CALLS. `ignore_index` is masked in `_loss_fn` for the same reason as JAX's — `mlx.nn.losses` takes no such argument (the METRICS need no such mask since 2026-08-05: `accumulate_confusion` takes `ignore_index` and drops those pixels before counting). **Apple silicon ONLY**, and the extra's `sys_platform == 'darwin' and platform_machine == 'arm64'` marker keeps `pip install deltaid[mlx]` succeeding (and empty) elsewhere. `registrations=None` like JAX's, and for the same reason.
- **The Shared Spec Is Implemented FIVE Times And They All Report 488,739 (2026-08-03, completes the `unet/` package):** `TorchUNet` / `KerasUNet` / `TensorFlowUNet` / `FlaxUNet` / `MlxUNet`, each checked against `spec.trainable_parameter_count` — the DERIVATION — rather than against whichever was written first, including under custom `widths` (pinned by `tests/test_unet_spec.py::test_all_five_implementations_agree_with_the_spec_and_each_other`). **Excluding batch-norm's running statistics takes a DIFFERENT mechanism in each framework and that is the wrinkle to know:** torch holds them as BUFFERS (`requires_grad` filtering does it), Keras as non-trainable WEIGHTS (`trainable_weights` does it), raw TensorFlow as `trainable=False` variables, Flax as `nnx.BatchStat` — a different variable TYPE in the same state tree, so counting `nnx.Param` only does it — and **MLX keeps them in the SAME parameter tree as the weights**, so there the exclusion is a NAME filter (`running_mean` / `running_var`) and without it the five-way match breaks. Every implementation IS its framework's own model type (`nn.Module` / `keras.Model` / `tf.Module` / `nnx.Module` / `mlx.nn.Module`), so no loop reaches THROUGH a wrapper. - **BINARY Segmentation Is `num_classes: 2` — There Is No Single-Channel Mode, And That Is DECIDED (2026-08-03, closes the TASKS question):** the ONE target contract is `[N, C, H, W]` logits against an int64 `[N, H, W]` class-id mask, and binary is `C=2`. A true `[N, 1, H, W]` + `BCEWithLogitsLoss` branch — what smp's `mode="binary"` losses expect — was evaluated and REJECTED: it would buy a second target shape, a second loss family, a second metric family and a second prediction contract, to reach a number the existing contract already reaches. **What a binary setup actually buys is NOT SCORING THE BACKGROUND, and that is a knob rather than a shape.** Measured on a ~2%-foreground mask with a model predicting nothing but background: `DiceLoss(mode="multiclass")` = **0.5052** (the background's perfect score halves it), `MulticlassJaccardIndex(average="macro")` = 0.4897 (same dilution), against `DiceLoss(mode="multiclass", classes=[1])` = **0.9999** and `DiceLoss(mode="binary")` = 0.9899 — i.e. smp's OWN `classes=` knob, over the C=2 contract, gives the binary signal. And `MulticlassJaccardIndex(average=None)` reports `[0.9795, 0.0]`, which the per-class table now renders worst-first so the `0.0` is the FIRST row. So the answer to "how do I do binary?" is a config (`classes: [1]` + a per-class metric), documented in the README, and NOT a branch in this project. Do not reopen it by adding a `mode:` knob to the segmenter.
- **The Keras UNION Is FINAL, Not A Placeholder — Keras Ships No Phase-Scoped Metric Hook (2026-08-03, closes the TASKS question):** verified against Keras **3.15.1**: `Model.compile` takes `metrics` and `weighted_metrics` and NOTHING phase-scoped (`weighted_metrics` is about sample weights); the set lives in ONE `CompileMetrics` container; and `Model.metrics` is a read-only property (`fset is None`). - **`num_classes` Resolution — model head → explicit → lazy kwarg → WALK the masks (2026-08-02, closes the old TASKS item):** `initialize()` resolves it, and the order matters. For `task="fit"`: a concrete model's `num_classes` (authoritative — metrics sized against anything else mis-score the head), then the explicit ctor arg, then a `!lazy:` model's pinned kwarg, then **`recordstream.num_mask_classes(train_set, target_key)`**, which walks the mask column and takes `max + 1`. - **What A Run RECORDS Is Named `<split>/<name>` On EVERY Backend (2026-08-04):** every tracker writes the key it is handed, verbatim, and eight engines spell the same quantities eight ways — `val_loss` (keras / jax / mlx), `valid_loss` plus UNPREFIXED validation metrics (fastai), `eval_loss` (a `transformers.Trainer`), `val/loss` (lightning / torch). So each backend TRANSLATES out of its engine's vocabulary on the way to a tracker and to the metrics sidecar — `as_metric_names(self.metric_names)`, declaring its own `source=` — and every one of them records `train/loss`, `val/loss` and `val/<metric>`, the same prefix the per-class tables already carry (`val/iou_per_class`). The vocabularies are matrainer's (`matrainer.metric_names`; rationale in its `docs/architecture.md` record 6) because the classification task needs the identical table on the identical eight engines — the `metric_slots` argument, one layer up. **`source` is per-CALL and `target`/`renames` are per-CONFIG, which is what makes ONE key work for eight backends:** only the backend knows which engine wrote the names and which split an unprefixed key is from (fastai's bare `dice_multi` is a VALIDATION metric where Keras's bare `mean_iou` is a training one), while a top-level `metric_names: !class:matrainer.MetricNames {target: keras}` broadcasts into all eight ctor slots. **Four details that are silent when wrong:** (1) `LightningSegmenter.training_step` logs the loss TWICE — `train/loss` (`on_epoch=True`) and `train/loss_step` (`on_step=True`, `prog_bar`) — because Lightning appends `_step`/`_epoch` only when ONE name carries both, and `train/loss_epoch` is a name no other backend writes; All four are declared CONSTRUCTOR params sharing one `MetricsSpec` alias (a post-construction-only slot is invisible to `to_pydantic`, so navigaitor's form-spec and StreamStudio would never offer it), and each is DUAL-PURPOSE the way `model` is — it holds that split's SPEC until `initialize()` builds it, and the live prefixed `MetricCollection` after. **`_metrics_built` is not a tidiness flag:** `run()` calls `initialize()` every time and `is None` cannot tell "not built yet" from "wired with a spec", so without it a second `initialize()` re-prefixes `val/` into `val/val/`. Pins: the `TestTheTrainingSplitReducesOncePerEpoch` group in `tests/test_lightning_segmenter.py`, plus the metric-slot groups in each backend's suite.
- **A METRIC IS ACCUMULATED OVER THE SPLIT, NEVER AVERAGED PER BATCH — And The Arithmetic Is matrainer's (2026-08-05):** the three backends that own their loop and resolve metrics by NAME (`jax` / `mlx` / `huggingface`) each held a private numpy/jnp/mx implementation of `mean_iou` / `pixel_accuracy` / `iou_per_class`. All three now name `matrainer.metric_functions` — `mean_iou` / `overall_accuracy` / `iou_per_class` over a `C×C` confusion matrix the loop accumulates and reduces ONCE per split. **For `jax` and `mlx` that is a BUG FIX and for `huggingface` it is not, and the difference is worth knowing rather than flattening:** those two averaged a per-batch value, which for mean IoU is wrong in a way that MOVES WITH THE BATCH SIZE (a class absent from a batch is SKIPPED by that batch's mean, so batches with fewer classes present are over-weighted — 10 classes at accuracy 0.7 against an exact 0.5922 reads 0.6164 at batch 4 and 0.5798 at batch 32). **On THIS example's data the gap is 1.4e-5 and that is not reassuring, it is the reason to fix it structurally:** measured through the real JAX loop on the 64-row val split, accumulated 0.104803 against batch-averaged 0.104790 — eight batches of eight 224x224 images all contain the three classes in similar proportions, so the means nearly coincide. The gap opens with more classes, smaller batches or sparser ones, and nothing in a config tells a reader which regime they are in. Do NOT cite the sweep's jax/mlx-vs-torch `val/mean_iou` spread as evidence of this: that is the MODELS differing (and `tensorflow` sits in the same cluster while never having been per-batch at all). `huggingface` never was, because `batch_eval_metrics` is False by default and a `Trainer` therefore gathers the WHOLE split and calls `compute_metrics` ONCE (verified) — its hand-written numpy agreed with the shared functions to ten decimals on real arrays. What the swap buys THERE is that the two cannot drift, plus `iou_per_class`, which its own registry never had. **The partition is by NAME, before resolution** (`_partition_metrics`), which is why only a NAMED metric can be confusion-based: nothing here can know what a user-supplied CALLABLE would want accumulated, so one keeps the `(logits, labels, ignore_index)` protocol and its per-batch mean. **ONE line of this is engine-specific and it is silent when wrong:** `accumulate_confusion` argmaxes the LAST axis, so the huggingface backend moves its `[N, C, H, W]` channel axis first (`np.moveaxis(upsampled, 1, -1)`) — get it wrong and the model is scored against its own WIDTH, which produces a plausible number and no error (pinned by a non-square check, since `H == W` would still run). **The property that pins accumulation without restating the arithmetic is BATCH-SIZE INDEPENDENCE** — the same model over the same rows at two batch sizes must give one number — checked through the REAL epoch loop in both `tests/test_jax_segmenter.py` and `tests/test_mlx_segmenter.py`; the arithmetic's own agreement with torchmetrics is matrainer's to pin. The torch backends were always right (torchmetrics accumulates internally), which is what makes them the reference the other five now match. Rationale: `docs/architecture.md` record 14.
- **A NON-SCALAR Metric Is REPORTED Through The Text Channel, Never Through `log_dict` (2026-08-02, closed 2026-08-03):** `log_dict` reduces every value through Lightning's `convert_tensors_to_scalars`, which RAISES on anything that is not one number — so a per-class IoU (`average=None` -> a `[C]` vector) would kill the validation loop on the first epoch if handed to it. `_report_epoch_metrics` therefore computes ONCE at epoch end, passes only `scalar_metrics(...)` to `log_dict`, and hands the same computed mapping to `_report_per_class`, which sends every VECTOR to the log and to each tracker's `log_text` (plus `log_figure` when `plot_metrics: true`). Reset happens at epoch START, not end, so the last epoch's state survives for the sidecar and the `computed_metrics` `@output`. **The selection rule and the renderers are matrainer's, not ours** — `per_class_vectors` / `render_vector_as_table` / `render_vector_as_figure` — and the rule is by SHAPE (a flat numeric sequence of length >= 2), never by metric NAME, so a backend cannot need a naming convention nothing enforces; this project decides only WHEN and WHERE. **It is a different rendering from the classification task's and that is the point, not an oversight:** there the useful non-scalar is a square confusion MATRIX (a heatmap), here it is a per-class VECTOR — one axis of meaning, a shared scale, and what a reader wants is a RANKING. So the table is sorted WORST-CLASS-FIRST and the figure is a sorted bar chart with the mean as a reference line; do NOT close a future gap here by reusing the confusion-matrix path. **`class_names:` is a CONFIG knob here, unlike classification**, which derives them from a label map — a mask carries class IDS and nothing names them, so unset means the rows are numbered. `TorchSegmenter` reports identically from `_epoch_metrics`, and that matters more than it looks: the two backends exist to be compared, so a metric one silently dropped would make the comparison a lie. **Verified end to end 2026-08-03:** on the 256-row Oxford-Pets slice both backends print `val/iou_per_class (mean 0.7509)` with boundary 0.4827 / pet 0.8549 / background 0.9150 — i.e. the per-class table shows the void-ish boundary ring dragging a mean that looks healthy.

- **The CORE Is Backend-Free; A Framework Belongs To Its Extra (2026-08-02):** `pip install deltaid` gives the CLI and config surface only — `torch` / `pytorch-lightning` / `torchmetrics` / `segmentation-models-pytorch` / `albumentations` live in `[lightning]`. **Every backend-owned name in `deltaid/__init__.py` is therefore LAZY (PEP 562)**, mapped to `(module, extra)` so `import deltaid` pulls NO framework and touching a missing one raises an `ImportError` naming the exact extra rather than a traceback from three libraries down.
